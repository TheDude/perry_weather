# weather-sensor (Python)

Reads observations from the RS485 weather sensor (9600 8N1, 9-byte
little-endian frames, CRC-16/MODBUS) on a serial port and logs them to the
systemd journal. Runs as a systemd service.

```
frame_parser.py          CRC check + streaming frame decoder
weather_sensor.py        open the port, read, print
weather-sensor.service   systemd unit
tests/                   parser unit tests
scripts/mock.py          sensor mock from the exercise
scripts/demo.sh          socat + mock + service, end to end
```

## Requirements

Python 3.7+ and pyserial (`apt install python3-serial` or `pip install pyserial`).

## Run

```bash
python3 -m unittest -v                 # parser tests
CORRUPT=0.2 scripts/demo.sh 20         # end-to-end against the mock for 20 s

# or by hand
socat -d -d pty,raw,echo=0,link=/tmp/ttyMOCK pty,raw,echo=0,link=/tmp/ttyMOCK_PEER
python3 scripts/mock.py --serial /tmp/ttyMOCK --sensor a
python3 weather_sensor.py /tmp/ttyMOCK_PEER
```

## Install as a service

```bash
sudo mkdir -p /opt/weather-sensor
sudo cp weather_sensor.py frame_parser.py /opt/weather-sensor/
sudo cp weather-sensor.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now weather-sensor
journalctl -u weather-sensor -f
```

The port is set in the unit's `ExecStart` line (`/dev/ttyUSB0`); edit it there
or with `systemctl edit weather-sensor`.

## Output

```
temperature=22.1C humidity=55.7%RH
wind=3.0m/s rain=0.2mm
dropped frame (crc_mismatch): aa 55 01 dd 00 30 02 87 62
```

Each line is printed with a syslog priority prefix (`<6>` info, `<4>` warning,
`<3>` error). journald strips it and stores it as the entry's priority, so
`journalctl -u weather-sensor -p warning` shows only problems. Run by hand, the
prefixes are visible.

## Design notes

- **Logging is `print`.** systemd sends a service's stdout to the journal, and
  the spec asks for nothing more. `flush=True` because under systemd stdout is
  a pipe, which Python block-buffers.
- **Parsing.** `FrameParser.feed()` takes whatever bytes arrived and returns
  the frames that completed, so it doesn't care how reads line up with frames.
  It finds `AA 55`, waits for 9 bytes and checks the CRC. On a bad frame it
  skips one byte and searches again rather than skipping all 9, so a false
  `AA 55` in noise can't swallow a real frame that starts inside it.
- **Errors.** CRC failures are logged with the raw bytes and skipped. A
  serial error (device unplugged) exits with status 1 and systemd restarts the
  service after 5 s (`Restart=on-failure`), so there is no retry loop in the
  code.
- **Runs as root.** No environment or security constraints were given, and on a
  dedicated embedded device that's a reasonable default. Running as a normal
  user would be `User=` plus `SupplementaryGroups=dialout` in the unit.
- **Units.** Values are int16 tenths (degC, %RH, m/s, mm per the mock; rain is
  accumulated since the previous wind/rain packet), formatted with integer math
  so `-5` prints `-0.5`.

## Mock / spec discrepancies

- `mock.py`'s framing comment says the CRC covers bytes `[0..7]`; its code and
  the exercise README cover 0–6. I followed the code; the tests include frames
  generated by the mock.
- The mock's docstring mentions GPIO gating, but there is no GPIO code.
